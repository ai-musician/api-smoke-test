RAG Slack Bot — Architecture

A hybrid-search knowledge assistant for Slack. Each team configures its own data sources, triggers, and answer style — one system, isolated per team.

What step 6 means — “chunks + question”

A chunk is ~1,000 characters of source text (diagram 2). Step 6 hands Claude the question plus those chunks: “Here is the question, here is the source text. Answer using ONLY this.”

That suppresses hallucinations — it does not stop them. The prompt tells Claude to ignore its own memory and quote only the chunks, which is why answers can cite. But instructions are not hard constraints, which is why the gate below exists.

The Confidence Gate. If the best chunk scores below the threshold — 0.75 Confluence, 0.82 curated Q&A — the bot returns “I don’t know” and logs a knowledge gap.

The actual hybrid query — one call, one round trip

Both vectors go to Pinecone as parameters of a single index.query(). Scoring and merging happen server-side. This is a read — nothing is written.

results = index.query(
    vector=question_embedding,        # dense — meaning search (1024 floats, Titan v2)
    sparse_vector=sparse_embedding,   # sparse — keyword weights (BM25)
    namespace=team_namespace,         # only this team's data
    top_k=10,                         # best chunks, combined score
)

How This Is Tested 106 TESTS · ~4s

You cannot test a system like this by checking it returns an exact answer, because the answer is never exactly the same twice. So the suite splits in two. Deterministic tests cover the plumbing — parsing, chunking, API wiring — where exact assertions work. Probabilistic tests cover the AI’s behaviour — what it retrieves, how it ranks, when it refuses — and check rates and averages across a fixed set of sample questions instead.

The Test Cases

  1. Staying quiet when it doesn’t know the answer abstains_on_unknown_questions

    What it means: When asked questions our documents don’t cover, the bot must admit it doesn’t know at least 75% of the time. This is what keeps it from making things up.

  2. Answering when it should know known_questions_do_not_abstain

    What it means: The balance to the first test. A bot that said “I don’t know” to everything would pass test 1 perfectly and be completely useless. This one makes sure it actually answers at least 90% of the questions it does have the information for.

  3. Finding hidden problems in one topic cohort_gate_catches_what_aggregate_misses

    What it means: This test deliberately breaks the bot’s answers for a single topic to prove the test suite itself works. Even when the overall average score still looks healthy, the per-topic check has to notice and flag the one broken area.

  4. No slip against the known-good version no_distribution_drift_vs_baseline

    What it means: Before shipping an update, the new numbers — match scores, how often it answers, how often it says “I don’t know” — are compared against a saved gold-standard baseline. If they move too far from it, the build fails.

  5. Finding exact matches exact_token_match_wins

    What it means: AI is good at general concepts and bad at exact terms — a ticket number like ENG-1234, a release like 8.2. Neither means anything, so meaning-based search is weakest exactly where exact matches matter most.

2. Data Indexing Pipeline WRITE PATH

How knowledge gets INTO Pinecone — the write path. Six scheduled indexers run in the background, independent of the read path: if an indexer fails, the bot keeps answering from the existing index. Each chunk is stored with both a dense embedding and sparse BM25 term weights, plus source metadata (URL, title, last-updated).

Why both vectors are written, not just the dense one: re-embedding the corpus to add sparse retrieval later would mean a full re-index of every source. Writing sparse_values at index time is cheap; retrofitting it is not.

Here are the key techniques to prevent LLM hallucinations:

Step-by-Step Thinking

Force the AI to think out loud and break down its logic before giving a final answer. [1]

Strict Formats

Force the AI to answer using specific data formats so it cannot wander off-topic. [1]

The Confidence Gate

Monitor how confident the AI is. If the score is too low, block the answer instead of letting the bot guess. [1][3]

Human Verification

Require the bot to cite its exact sources so a human can easily double-check the facts. [1]

Strictly control the bot so it refuses to answer questions that are not in our company documents. Target metrics include: [2][3]

  • ≥90% answer rate on in-corpus (known) questions
Constant Tracking

Continuously monitor the bot's confidence scores and test for errors over time. [3]

Why the query takes both vectors

vector What the question means — matches paraphrases and different wording
sparse_vector The question's exact important words — catches ticket IDs, acronyms, product names. Meaning-based search is weakest exactly where exact matches matter most: a ticket number doesn't mean anything, so ENG-1234 and ENG-1235 land almost on top of each other.
namespace Team isolation — one index for the company, each team walled off
top_k Best chunks after Pinecone merges both scores server-side

The three calls, in order — who talks to whom

The orchestrator makes every call. Titan, Pinecone, and Claude never talk to each other.

Memory hook: Titan is the translator, Pinecone is the librarian, Claude is the writer. The translator turns the question into vectors, the librarian finds the ten best pages, the writer reads them and drafts the reply — and the orchestrator carries everything between them.

6. Feedback Loop — Flag → Verify → Retrieve WRITE PATH

The second write path: how a bad answer becomes a verified answer that's retrieved next time. The question is what gets embedded — because future queries resemble past questions, not past answers — and the answer travels in the metadata. Pinecone is the source of truth; Google Docs is a one-way export for human browsing.
